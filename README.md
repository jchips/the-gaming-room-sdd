# The Gaming Room SDD

The Gaming Room is a game development company that wants to make their Draw It or Lose It game software available on more operating systems. So far, the Draw It or Lose It game is available on Android and their next goal is to make a web-based version of the game. They have several requirements for the web-based software including that it must run on the web for all operating systems, the game will have the ability to have one or more teams involved, each team will have multiple players assigned to it, only one instance of the game can exist in client memory at any given time, and game and team names must be unique (no duplicates) and allow users to check whether a name is in use when choosing a team name.

In the documentation, I had a solid understanding of most concepts like the different operating systems and their pros and cons, how storage works, and distributed systems and networks, and I was able to explain them and how they relate to the client’s needs. To have the clients requirements listed in the design document was helpful when working with the code and going about which operating platform to use, as well as handling the storage and memory management. It is helpful to design the document for the purpose of making sure the development ideas are all feasible for the project and are possible within the specific limitations of the client. To improve the software design document, I would revise my design constraints section. What I wrote was more along the lines of requirements than constraints. A constraint that I could have listed is the time available to complete the project.

I tried my best to make to follow the client’s requirements and constraints while designing the document so that the development of the game application is specific to the client’s needs and available resources. I also thought about the future users of the software, especially when considering things like memory management and security. I kept the IEEE Code of Ethics in mind. Users will not choose to use software that they don’t feel is safe or user friendly or that harms their phone in some way. Considering the user’s needs means better business and also is the best way to gain user’s trust when it comes to future software, and to avoid lawsuits.

To design the software, I factored in the client’s requirements and created a UML diagram that aligned with all their wants and requests. This was helpful for mapping out the code by giving me an idea of what the project will look like and how is will function. Security is important for both the client and users so I prioritized effective security ideas. For instance, authentication and authorization is a good start to protect the users’ data, so that means a server must be involved. The next step was to decide how best to manage the server (traditional vs serverless). For future projects, I think a good strategy will be to begin with writing down all requirements and design constraints and then analyzing what software and hardware will be required for the project based on that. If I know what will the project will need in both software and hardware in ordered to be developed, then I can assess the resources needed, the estimated cost, and the best way to start the development process.
